# 14. Правила FSD в проекте

Обязательные правила раскладки кода по Feature-Sliced Design. Описание текущей структуры — в [02. Feature-Sliced Design](./02-feature-sliced-design.md), автоматические проверки — в [08. Линтинг и качество](./08-linting-and-quality.md).

Правила проверяются тремя инструментами:

| Инструмент                       | Что ловит                                                      |
| -------------------------------- | -------------------------------------------------------------- |
| `eslint-plugin-boundaries`       | импорт из вышележащего слоя                                    |
| `no-restricted-imports` (ESLint) | относительные пути между слоями, кросс-entity импорт без `@x/` |
| Steiger (`npm run fsd`)          | обход публичного API, лишние слайсы, именование сегментов      |

Перед PR должны проходить `npx tsc --noEmit`, `npm run lint` и `npm run fsd` (без ошибок; предупреждения `insignificant-slice` допустимы, см. ниже).

---

## 1. Слои и направление зависимостей

```
app → pages → widgets → features → entities → shared
```

- Слой импортирует **только из слоёв ниже**. Импорт вверх — ошибка.
- Слайсы одного слоя **не импортируют друг друга**. Исключение — `entities` через `@x/` (п. 5).
- `app` и `shared` не делятся на слайсы, поэтому внутри них импорты между папками разрешены.
- Корневой `app/` (Next.js App Router) — не FSD-слой. Каждый файл в нём — однострочный реэкспорт: страницы из `src/pages`, каркас из `src/app/layouts`, обработчики API из `src/app/api`. Логику и разметку туда не класть. `default`-экспорт, которого требует Next.js, получается переименованием: `export { Home as default } from '@/pages/home'`.

## 2. Что в каком слое

| Слой       | Кладём                                                                                                                                         | Не кладём                                                               |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `app`      | провайдеры, корневой стор (`Root`, начальное состояние, история), глобальные стили, каркас `RootLayout`, серверные обработчики API (`app/api`) | UI экранов, бизнес-логику                                               |
| `pages`    | композицию страницы из виджетов и фич                                                                                                          | собственную логику и стейт                                              |
| `widgets`  | самостоятельные блоки интерфейса: композицию фич и сущностей (`SceneViewport`, `Sources`, `Layers`)                                            | переиспользуемые действия пользователя                                  |
| `features` | **одно действие пользователя** над сущностями: строить кубы, трансформировать модель, выбрать инструмент, загрузить модель                     | отображение сущностей без действия                                      |
| `entities` | бизнес-сущности: MST-модели, их хуки, «немое» отображение (`GLTFModel`, `CubeMaterial`, `Camera`)                                              | обработчики пользовательских действий, композицию других сущностей в UI |
| `shared`   | всё, что не знает о предметной области: UI-кит, `lib/*`, клиент API                                                                            | доменные модели и типы, хуки конкретных слайсов (`useStoreScene`)       |

Проверочный вопрос для `shared`: «Можно ли перенести это в другой проект без изменений?» Если нет — место в `entities` или выше.

Проверочный вопрос для `entities` и `features`: «Компонент меняет стор по действию пользователя?» Если да — это фича.

Синхронизация стора с тем, что уже отрисовано, действием пользователя не считается и допустима в `entities`. Например, `GLTFModel` сохраняет габариты загруженной модели (`model.setSizes`), а `Camera` после остановки камеры записывает дистанцию (`camera.setRealTimeDistance`). Обработчик не принимает решений и не меняет предметные данные, он только отражает в сторе текущее состояние сцены.

Код, нужный только одной фиче, живёт в её сегменте `lib`, а не в `shared`. Например, `getCubePosition` лежит в `features/build-cubes/lib`.

## 3. Сегменты

Внутри слайса код делится на сегменты **по назначению**:

| Сегмент  | Содержимое                                                  |
| -------- | ----------------------------------------------------------- |
| `ui`     | React-компоненты и их стили                                 |
| `model`  | MST-модели, хуки стора, типы, моки данных                   |
| `api`    | запросы к серверу                                           |
| `lib`    | вспомогательные функции слайса                              |
| `config` | константы и фабрики начальных данных (`createDefaultTools`) |

- **Пустых сегментов не создавать.** Файлы вида `export {}` удаляются. `create-slice` создаёт только `ui`, остальное — по мере необходимости.
- Сегменты называются по назначению, а не по сути (`model`, а не `types`, `hooks`, `utils`).
- В `shared` сегменты называются по области: `shared/lib/mst`, `shared/lib/three`, `shared/lib/keyboard`, `shared/lib/styles`. Папки `shared/utils` и `shared/lib/debug` не используются: отладочный код кладётся в сегмент той области, к которой относится (`useMSTDebug` — в `shared/lib/mst`).

## 4. Публичный API

- У каждого слайса есть `index.ts`. Снаружи импортируем **только** из него: `@/widgets/notes`, а не `@/widgets/notes/ui/notes`.
- В `shared/ui` и `shared/lib` публичный API — индекс каждого сегмента: `@/shared/ui/button`, `@/shared/lib/mst`, `@/shared/lib/styles`.
- Внутри слайса используем относительные импорты (`./scene-canvas`, `../model/mock-sources`), а не свой же баррель.
- Индекс реэкспортирует только то, что нужно снаружи. Внутренние компоненты фичи (`BuildableCube`, `CubePlaceholder`) в индекс не попадают.
- **Только именованные экспорты.** `export default` ломает `export *` в барреле и заставляет обходить публичный API.

## 5. Кросс-entity импорт через `@x/`

Если сущность `A` использует сущность `B`, `B` публикует для неё отдельный файл `entities/B/@x/A.ts`:

```ts
// src/entities/mesh/@x/scene.ts
export { MCubeMesh } from '../model/cube-mesh';
export { MModelMesh, MModelExternalMesh, MModelInternalMesh } from '../model/model-mesh';
```

```ts
// src/entities/scene/model/construct/construct.model.ts
import { MCubeMesh, MModelInternalMesh } from '@/entities/mesh/@x/scene';
```

- Файл `@x/` называется по **потребителю**.
- `@x/` не реэкспортируется из `index.ts` сущности.
- Слои выше (`features`, `widgets`) импортируют сущность через обычный `index.ts`.

## 6. Стор MST и слои

- Корневая модель `Root` и `RootStore` живут в `src/app/store`. Там же начальные данные и подключение `withHistory`.
- `shared/lib/mst` даёт только общий `useStore()` и пустой интерфейс `IStore`; `app` расширяет его через module augmentation.
- Хук доступа к части стора принадлежит сущности: `useStoreScene` — в `entities/scene`, `useStoreProfile` — в `entities/profile`.
- Модели, которые описывают предметную область (`MTexture`, `MCubeMesh`), — в `entities`. В `shared/lib/mst` — только доменно-нейтральные модели и миксины (`MUrlOrCache`, `withMatrix4`, `withHistory`).

## 7. Композиция вместо зависимостей

Если сущности нужен интерактив из фичи, сущность его **не импортирует**. Склейка происходит уровнем выше:

```tsx
// src/widgets/scene-viewport/ui/scene-models.tsx
isEditable ? (
	<TransformControls id={model.id}>
		<GLTFModel model={model} />
	</TransformControls>
) : (
	<GLTFModel model={model} />
);
```

Так же страница передаёт фичу в виджет через слот: `<SceneViewport toolbar={<ToolbarScene />} />`.

## 8. Именование

- Папки слайсов и файлы — kebab-case. Слайс фичи называется действием: `build-cubes`, `transform-mesh`, `select-tool`, `upload-model`.
- Имя файла совпадает с компонентом в kebab-case: `SceneViewport` → `scene-viewport.tsx`.
- Моки данных — `model/mock-*.ts`, константа `MOCK_*`.
- Подробнее — в [13. Процесс разработки](./13-development-workflow.md#соглашения-об-именовании).

## 9. Предупреждения Steiger `insignificant-slice`

Steiger предупреждает о слайсах, у которых ноль или одна ссылка. В проекте это допустимо:

- виджеты страницы Platform используются один раз, но это самостоятельные блоки, которые будут переиспользоваться;
- фичи `build-cubes` и `transform-mesh` подключены только в `widgets/scene-viewport`, а `select-tool` — только в `pages/platform`. Это отдельные действия пользователя: их можно заменить или подключить в другом месте, например в режиме просмотра без строительства;
- `pages/home` и `pages/platform` используются из корневого `app/`, которого Steiger не видит;
- заготовки (`widgets/chat`, `widgets/properties`, `features/upload-model`) ещё не подключены.

Ошибки Steiger (`✘`) допустимыми не считаются.

## 10. Чек-лист ревью

- [ ] Нет импортов из вышележащих слоёв и между слайсами одного слоя (кроме `@x/`).
- [ ] Импорты снаружи слайса идут через его `index.ts`.
- [ ] Нет `export default` в `src/`.
- [ ] Нет пустых сегментов и файлов `export {}`.
- [ ] В `shared` нет доменных моделей, типов и хуков конкретных слайсов.
- [ ] Обработчики действий пользователя лежат в `features`, а не в `entities`.
- [ ] `tsc`, `lint` и `fsd` проходят.
